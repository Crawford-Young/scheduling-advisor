# Project notes (Cybond)

- Workspace standards live in `~/code/CLAUDE.md` — pnpm only, TDD, 100% statements/functions/lines coverage (branches ≥97%), Conventional Commits, rebase-only git.
- **`WeekCalendarView` never resyncs from props.** It seeds internal state once and applies move/resize/delete/drag-create optimistically. `CalendarClient` restores server truth by remounting via `key={weekStart-resetKey}`; after create, a dedicated `useTransition` + `resyncQueuedRef` delays the `resetKey` bump until `router.refresh()` completes (bumping synchronously remounts with stale props). Do not "simplify" this machinery.
- **Type taxonomy is `task` + `goal` (Wave 2.1).** The `habit` type was removed — habits are recurring tasks (`recurrence` column). `createTaskSchema` rejects `type:'habit'`. The `createHabit` server action still exists as a live AI-chat tool (inserts `type:'task'` + `recurrence:'daily'`) — do not delete it; the library `ActionConfirmCard`/`ChatPanel` entityType union still emits `'habit'` and the chat renderer path must keep handling it.
- **Everything-lib architecture (Wave 2.2):** `WeekCalendarView` + `ActivityFormDialog` ship from `@crawfordyoung/ui` (0.18.0); the app supplies data wiring only. Calendar chip complete-toggle wires `onEventToggleComplete` → `recordCompletion` (recurring, completing) or `updateTask` (status: pending|completed); toggled-event direction is load-bearing (library passes the TOGGLED completed value). Goal `targetDate` is emitted date-only and converted to noon-UTC ISO (`T12:00:00.000Z`) before `createTaskSchema` (`.datetime()` schema rejects date-only; avoids goal-date-wipe trap). Per-type `TaskFormDialog`/`GoalFormDialog`/`HabitFormDialog` and quick-add bar deleted in Wave 2.1.
- **Calendar drag-create uses the library's inline popover** (`WeekCalendarView.onEventCreate` → app `handleEventCreate` → `createTask`), not a dialog. The popover emits `recurrenceFrequency: daily|weekly|monthly|yearly`; app fan-out only expands daily/weekly/monthly (`yearly` persists but never fans out — known gap).
- **Chip lock (`@crawfordyoung/ui` ≥0.19.0, Wave 2.4):** `tasks.locked` (migration 0014) seeds the chip's lock icon via `toLibraryEvent`; `updateTaskSchema` gained an optional `locked: z.boolean().optional()` field, passed through untouched by `updateTask`. Toggle wiring is view-level — `WeekCalendarView`'s `onEventToggleLock` prop (the chip-level prop is the differently-named `onToggleLock`; do not conflate them) calls `handleToggleLock`, which reads the row's PERSISTED locked state from `events` (not the library's optimistic event) and flips it via `updateTask({ id, locked: !currentlyLocked })` — a server-truth flip, not a library-optimistic-value flip. Lock scope is move/resize ONLY: the library gates drag/resize client-side on `event.locked` (resize handles disappear, pointer-down for move is a no-op) while complete-toggle, edit, and delete stay fully available on a locked row. There is NO server-side startAt/endAt guard by design (spec amendment) — the lock is a UI-only gate.
- **Recurrence series (wave 2.3):** `tasks` carries `recurrence_group_id` (uuid linking fanned occurrence rows), `recurrence_days` (jsonb weekday array, weekly only — null on interval paths for createTask parity), and `recurrence_count` (weeks). `updateTaskSeries` (`src/server/actions/tasks.ts`) is the series-edit action: **future-only semantics** — regenerated/materialized rows are filtered to `startAt > now` ("this and following"); past rows are never touched. A one-off row (null group id, non-null `startAt`) given a series frequency **materializes**: fresh group id, anchor updated in place (id/startAt/status untouched), future occurrences fanned out skipping the anchor's slot — no delete on that path. Goals are excluded from series routing on both surfaces (`calendar-client.tsx`, `use-activity-actions.tsx`); the routing predicate treats emitted days presence / recurrence change / count change as the series-edit signal.
- **Recurrence UI seeding + routing (S9, `@crawfordyoung/ui` 0.18.0):** the app seeds edit surfaces via `CalendarEvent.seriesDays` (edit-seed field, decoupled from display) — NEVER seed library `recurrenceDays` on calendar events; that field drives WeekCalendarView's display fan-out and each DB row is already one materialized occurrence. Dialog `initialValues` seeds `recurrenceDays`/`recurrenceCount` from the row. A seeded picker re-emits days on EVERY save, so series-edit routing compares emitted vs persisted days with order-insensitive set equality (`sameDaySet` — duplicated in `calendar-client.tsx` and `use-activity-actions.tsx`; shared recurrence-routing module is a next-touch candidate); reordered-same-set saves route to `updateTask` so time-only edits keep their time change. All four surfaces thread `recurrenceDays` + `recurrenceCount` to the server: popover create, chip popover edit, dialog create (`activity-create-button.tsx` — S6 QA fix: it previously dropped days plus color/location/description/allDay), dialog edit.
- **Group streaks (derive-on-read):** no stored counter — `computeGroupStreak` (`src/lib/streaks.ts`) derives `{current, best}` from the group's due occurrences (status + `startAt <= now`) at read time; every row/chip of a group shows the same value. Grace rule: the current-streak backward walk skips a pending occurrence dated today (UTC day — the day isn't over) but breaks on any older non-completed due occurrence; best-streak has no grace. Group id stamping: `createTask` fan-out shares one fresh `recurrence_group_id` across its inserts; `updateTaskSeries` materialization stamps a new one on the anchor + fan-out; migration 0013 backfilled ids for pre-2.3 fanned rows.
- **Local-wall-clock invariant (`@crawfordyoung/ui` ≥0.19.0):** the three UTC/local-mixing bugs tracked in `~/code/docs/scheduling-advisor/issues/2026-07-06-w2.3-issues.md` (phantom overnight chip from UTC-substring day judging, chip edit popover seeding the UTC clock, dialog-typed times stored as a UTC clock) are all fixed. The invariant going forward: typed/displayed times are LOCAL wall-clock — `buildIso`/`toTimeSlot` and `splitOvernightEvents`' day-membership check all read/write via local `Date` getters (`getFullYear`/`getMonth`/`getDate`/`getHours`/`getMinutes`), never UTC ISO substrings. The persisted/round-tripped ISO on `CalendarEvent.start`/`end` is always a real UTC instant — only the LOCAL reading of that instant changed. Any app code that derives a calendar "day" from an ISO string must use local `Date` getters to match the library, not UTC substring slicing.
- **Calendar wake→sleep window semantics (library override trap):** when `sleepEnabled=true`, `WeekCalendarView` forces a full 24h grid (`hourStart`/`hourCount` are IGNORED) and renders shaded sleep zones where drag-create is blocked. Windowed view therefore needs `sleepEnabled=false` + `hourStart`/`hourCount`; full-day view needs `sleepEnabled=true`. Wiring it inverted ships a dead window that mocked unit tests cannot catch (caught at the Wave 2.1 Preview Gate).
- **`TaskTimeFields` + `buildIso`/`toTimeSlot` live in `@crawfordyoung/ui` (≥0.13.1), not in the app.** `ActivityFormDialog` consumes them; don't reintroduce a local copy. See the local-wall-clock invariant above (0.19.0) for their semantics.
- **Goals/Tasks are unified into one `/activities` destination** backed by the single polymorphic `tasks` table (no per-type table). The `/goals`, `/habits`, `/tasks` routes were removed (Wave 2); the auth proxy redirects every unauthenticated path to `/login`, so a removed route is indistinguishable from a protected one in the unauthenticated e2e suite (a 404 is unobservable there — assert the `/login` redirect instead). Activities has search (`?q=`, debounced buffered input + `router.replace`), type/status filters, and a recurring toggle.
- **Wake/sleep hours persist to `calendarPrefs.workingHoursStart/End`** via `setCalendarWindow` (Settings → Calendar section, defaults 9/17 when no row). `getCalendarPrefs` returns `null` for no row — callers must default.
- **Per-day wake/sleep windows:** `calendarPrefs.dayOverrides` is jsonb with keys '0'–'6' (Sun-first) and values `{wake, sleep}` in minutes-since-midnight. `resolveDayWindows` (`src/lib/calendar-windows.ts`, safeParse fallback + Sentry) merges per-day overrides with global hours. Converted to fractional hours at the calendar page boundary for the library's `dayWindows` prop. Zod schema: `src/lib/schemas/calendar-prefs.ts`.
- **App-wide 12/24h preference:** `calendarPrefs.use24h` boolean, threaded server-side from both calendar and activities pages into `WeekCalendarView` and library `ActivityFormDialog`.
- **TTL auto-delete:** `calendarPrefs.ttlDays` (nullable int, 1–365 days). Pending one-off events hard-deleted N days after end on calendar/activities read paths; completed events + streak history untouched. `safeDeleteExpiredEvents` in `src/server/actions/event-ttl.ts`.
- **Schema migrations:** 0011 added `day_overrides` jsonb + `use_24h` boolean; 0012 converted `workingHoursStart/End` from hours to minutes, migrated `dayOverrides` values to minutes, added `ttl_days` integer; 0013 added `recurrence_group_id`/`recurrence_days`/`recurrence_count` to `tasks`, dropped the `streaks` table (streaks now derived on read — `computeGroupStreak` in `src/lib/streaks.ts` over the group's occurrence rows), and backfilled group ids for existing fanned rows; 0014 added `locked` boolean (default `false`, not null) to `tasks`, backing the calendar row-lock flag (Wave 2.4).
- **Dialog mocks in tests must surface data props** (render the values), not just component identity — identity-only mocks have hidden real contract bugs. And prop-value assertions against a mocked library component cannot catch the library overriding those props internally (the sleepEnabled trap above) — behavior that depends on library semantics needs the Preview Gate.
- **Two test trees, both run by vitest** (no `include` glob; only e2e excluded): co-located `src/**/*.test.tsx` AND `tests/unit/**`. Any component deletion/rename must clean both trees.
- Chat panel opens via `open-chat` CustomEvent; optional `detail.prefill` seeds the input. Listener must stay null-safe (`detail?.prefill`) — older dispatchers send no detail.
- E2E suite is deliberately unauthenticated (dummy `DATABASE_URL`, never touches the DB). Auth.js uses database sessions — authenticated e2e requires seeded postgres + forged session cookie and is its own planned wave.
- **Authenticated browser QA (proven 2026-07-07, wave 2.3 S6):** mint a dev session without touching credentials — insert a row into `sessions` (`session_token` = fresh uuid, `user_id` from `users`, `expires` +24h) via a one-off neon script, then set the httpOnly cookie `authjs.session-token=<token>` (domain `localhost`, path `/`, SameSite Lax) through Playwright's `context().addCookies`. Delete the session row when QA ends. This is the pattern the planned authenticated-e2e wave should build on. Two more things proven at wave 2.4 A4: (1) size the Playwright viewport tall enough to fit the full calendar grid without the calendar's own `overflow-auto` scroll container needing to scroll — its drag-create Popover anchors to the drag position and doesn't reliably reposition if that container scrolls mid-drag; (2) a long-lived dev server whose `node_modules` got a mid-session `pnpm` bump can keep serving a CSS bundle that's missing every Tailwind utility sourced ONLY from the library dist bundle (e.g. `group-hover:*`, bare `.group`) — confirmed via direct fetch of the served CSS chunk (zero `group-hover` occurrences) — so hover-only affordances may need `element.evaluate(el => el.click())` (a real DOM `.click()`, which bypasses hit-testing) instead of Playwright's `{force:true}` (which still respects live `pointer-events:none` at the browser's hit-test layer). A process restart alone does NOT fix it — turbopack's persistent `.next` cache re-serves the stale chunk (verified 2026-07-08: same chunk hash + zero `group-hover` after restart); wipe `.next` and restart after any mid-session dependency bump that feeds a Tailwind `@source` glob.
- Vitest auth-mock gotcha: `vi.mocked(auth).mockResolvedValueOnce(null as never)` — plain `null` fails type-check.
- **Spacing rhythm rules (Wave 2.2 audit, user-approved):** (1) every flow page container is `mx-auto max-w-5xl space-y-6` — chat is exempt (full-height surface); (2) `space-y-10` between page sections, `space-y-4` within a section; (3) horizontal control rows use `gap-3` within a group and `gap-4` between unrelated groups (calendar header toolbar included); (4) table cells: `whitespace-nowrap` on Date/Type/Status/Actions, `min-w-[12rem]` on Title — rows stay single-line, `overflow-x-auto` absorbs the rest.
- **`drizzle-kit migrate` can die silently on Windows** (its `@neondatabase/serverless` websocket path exits 1 with no error after "applying migrations..."). Fallback: one-off Node script with `drizzle-orm/neon-http/migrator` (`migrate(drizzle(neon(url)), { migrationsFolder: './src/db/migrations' })`) — same journal table, HTTP driver (the one the app itself uses). Delete the script after.
- **AI gating is token-balance-only.** `plan` is display-only (highlights the current tier on `/tokens`); no plan-based feature gates remain. Unauthenticated or zero-balance users see the app fully — only Cy chat and AI reflections require tokens.
- **`token-balance-changed` CustomEvent contract.** Dispatched on `window` after any token spend (chat `onFinish` callback). `TokenChipLive` in the app layout listens and refetches the balance via `getTokenBalanceAction`. Any new token-spending feature **must** dispatch `new CustomEvent('token-balance-changed')` on `window` so the topbar stays in sync.
