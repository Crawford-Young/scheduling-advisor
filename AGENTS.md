- **`WeekCalendarView` resyncs via `resyncToken` (`@crawfordyoung/ui` ≥0.20.0, Wave 2.5) — no remounts.** It seeds internal state once and applies move/resize/delete/drag-create optimistically; bumping the `resyncToken` prop's identity forces it to re-seed from the current `events` prop IN PLACE (never remounted, so in-calendar week navigation survives). `CalendarClient` routes every path through two helpers: `refreshAndResync()` (server-mutating success AND error paths — sets `refreshQueuedRef`, runs `router.refresh()` inside a tracked `useTransition`, and a `useEffect` bumps the token once that transition settles so the re-seed reads the FRESH events prop, not stale ones) and `resyncNow()` (immediate bump, no refresh — delete-cancel, plus the series-delete confirm path where the `events` prop is already filtered by the `hiddenGroupIds` overlay and the bump drops the group's chips instantly; an immediate re-seed replaces the library's internal state wholesale, so it can transiently revert an unrelated in-flight optimistic edit until that edit's own settle bump — accepted trade-off, Wave 2.6 S14). `confirmedRef` still discriminates delete confirm-vs-cancel so a confirmed delete's `onOpenChange(false)` does not fire a second immediate bump on top of the confirm path's bump. There is NO `key`/`resetKey` remount machinery — do not reintroduce it. **Any change whose visible effect flows through WeekCalendarView MUST state its resyncToken interaction explicitly in the task spec** — the library renders exclusively from internal `localEvents`, re-seeded ONLY on a token identity change, so "filter/modify the events prop" is invisible until a bump; regression tests for this class assert the token bump (pending-promise ordering), never the prop value, because mocked-lib unit tests render the prop directly and pass green on invisible changes (hit twice: sleepEnabled Wave 2.1, hidden-group overlay w2.6 S14 — opus impl + review both missed it). **Completed events are fully mutable** — edit, move, and resize all route through the normal `updateTask`/`rescheduleTask` persist paths like any other event; only the manual `locked` flag (set via the chip's lock toggle) gates move/resize, and that gate is enforced client-side by the library itself.
- **Calendar week URL sync (Wave 2.5):** `?week=YYYY-MM-DD` (validated in `calendar/page.tsx`) seeds `defaultWeekStart`; `WeekCalendarView.onWeekChange` mirrors in-calendar navigation back into the URL via `router.replace('?week=…', {scroll:false})`, preserving all other query params (`new URLSearchParams(window.location.search)` + `params.set('week', …)`). **Known limitation (spec-accepted, do NOT "fix"):** the library week is uncontrolled/seed-only, so browser back/forward changes `?week=` but the displayed week does not follow — only a reload re-seeds from the URL. The controlled-week alternative was rejected at debate.

Calendar chip complete-toggle wires `onEventToggleComplete` → `recordCompletion` (recurring, completing) or `updateTask` (status: pending|completed); toggled-event direction is load-bearing (library passes the TOGGLED completed value). Goal `targetDate` is emitted date-only and converted to noon-UTC ISO (`T12:00:00.000Z`) before `createTaskSchema` (`.datetime()` schema rejects date-only; avoids goal-date-wipe trap). Per-type `TaskFormDialog`/`GoalFormDialog`/`HabitFormDialog` and quick-add bar deleted in Wave 2.1.
- **Calendar drag-create uses the library's inline popover** (`WeekCalendarView.onEventCreate` → app `handleEventCreate` → `createTask`), not a dialog. The popover emits `recurrenceFrequency: daily|weekly|monthly|yearly`; app fan-out only expands daily/weekly/monthly (`yearly` persists but never fans out — known gap).
- **Chip lock (`@crawfordyoung/ui` ≥0.19.0, Wave 2.4):** `tasks.locked` (migration 0014) seeds the chip's lock icon via `toLibraryEvent`; `updateTaskSchema` gained an optional `locked: z.boolean().optional()` field, passed through untouched by `updateTask`. Toggle wiring is view-level — `WeekCalendarView`'s `onEventToggleLock` prop (the chip-level prop is the differently-named `onToggleLock`; do not conflate them) calls `handleToggleLock`, which reads the row's PERSISTED locked state from `events` (not the library's optimistic event) and flips it via `updateTask({ id, locked: !currentlyLocked })` — a server-truth flip, not a library-optimistic-value flip. Lock scope is move/resize ONLY: the library gates drag/resize client-side on `event.locked` (resize handles disappear, pointer-down for move is a no-op) while complete-toggle, edit, and delete stay fully available on a locked row. There is NO server-side startAt/endAt guard by design (spec amendment) — the lock is a UI-only gate. **Naming caution, extended (wave user-profiles):** the view-level prop set gated the same `onEvent*` way is 9 names total — `onEventCreate, onEventEdit, onEventDelete, onEventMove, onEventResize, onEventToggleLock, onEventClick, onEventRestore, onEventToggleComplete` (verified against `@crawfordyoung/ui` dist `index.d.ts:820-828`) — briefs/tests must copy these from the dist `index.d.ts`, never from memory; a wrong `onEventUpdate` shipped in a brief this wave.
- **Recurrence series (wave 2.3, superseded by wave 2.6 — see the grouped-row-writes entry below for current routing/guard rules):** `tasks` carries `recurrence_group_id` (uuid linking fanned occurrence rows), `recurrence_days` (jsonb weekday array, weekly only — null on interval paths for createTask parity), and `recurrence_count` (weeks). A one-off row (null group id, non-null `startAt`) given a series frequency **materializes**: fresh group id, anchor updated in place (id/startAt/status untouched), occurrences fanned out skipping the anchor's slot. Goals are excluded from series routing on both surfaces (`calendar-client.tsx`, `use-activity-actions.tsx`); the routing predicate treats emitted days presence / recurrence change / count change as the series-edit signal.
- **Series module surface (wave 2.6):** `src/lib/series-generation.ts` is the pure fan-out core (no auth/db — `generateSeriesRows` + window/weekday math), reused by every writer. `src/server/actions/series-mutations.ts` owns all grouped writes: `updateSeries` syncs shared fields group-wide and, on a pattern change, deletes pending rows and regenerates from the new pattern (completed/in-progress rows survive and are re-templated, never deleted — this replaces wave 2.3's future-only "this and following" filter); `extendSeries`/`safeExtendSeries` roll open-ended (uncounted) series forward on a fixed 8-week horizon, swept read-only-safe on every calendar/activities page read. `src/lib/series-consistency.ts` (`findSeriesDrift`/`reportSeriesDrift`) is a pure, read-path drift net — logs + Sentry only, never mutates — that flags a grouped-row shared-field mismatch the guards below should have prevented.
- **Recurrence UI seeding + routing (S9, `@crawfordyoung/ui` 0.18.0):** the app seeds edit surfaces via `CalendarEvent.seriesDays` (edit-seed field, decoupled from display) — NEVER seed library `recurrenceDays` on calendar events; that field drives WeekCalendarView's display fan-out and each DB row is already one materialized occurrence. Dialog `initialValues` seeds `recurrenceDays`/`recurrenceCount` from the row. Client-side day-set routing predicates are gone (Wave 2.6): grouped rows and rows edited TO a series frequency route straight to `updateSeries`, which decides field-sync vs pattern-rewrite server-side — the order-insensitive `sameDaySet` comparison now lives only inside `series-mutations.ts`. All four surfaces thread `recurrenceDays` + `recurrenceCount` to the server: popover create, chip popover edit, dialog create (`activity-create-button.tsx` — S6 QA fix: it previously dropped days plus color/location/description/allDay), dialog edit.
- **Group streaks (derive-on-read):** no stored counter — `computeGroupStreak` (`src/lib/streaks.ts`) derives `{current, best}` from the group's due occurrences (status + `startAt <= now`) at read time; every row/chip of a group shows the same value. Grace rule: the current-streak backward walk skips a pending occurrence dated today (UTC day — the day isn't over) but breaks on any older non-completed due occurrence; best-streak has no grace. Group id stamping: `createTask` fan-out shares one fresh `recurrence_group_id` across its inserts; `updateSeries` materialization (`src/server/actions/series-mutations.ts`) stamps a new one on the anchor + fan-out; migration 0013 backfilled ids for pre-2.3 fanned rows.
- **Grouped-row shared-field writes are series-only (Wave 2.6, S6).** Every grouped-row edit that touches a shared field (`title`/`recurrence`/`targetDate`/`startAt`/`endAt`/`color`/`location`/`description`/`allDay`) MUST go through `updateSeries` (`src/server/actions/series-mutations.ts`) — the old wave 2.3 per-action series editor it replaced is deleted. `updateTask` and `rescheduleTask` now server-reject any such write on a grouped row (`row.recurrenceGroupId != null`) with `'Grouped rows are series-managed — use updateSeries'`; calling either on a grouped row's shared fields is a defect, not a valid alternate path — this is a review-gate item. Per-occurrence fields (`status`, `locked`) are unaffected and stay writable on grouped rows via `updateTask`; `rescheduleTask` has no per-occurrence carve-out (it only ever writes shared time fields, so any grouped call to it is itself the defect).
- **Local-wall-clock invariant (`@crawfordyoung/ui` ≥0.19.0):** the three UTC/local-mixing bugs tracked in `~/code/docs/scheduling-advisor/issues/2026-07-06-w2.3-issues.md` (phantom overnight chip from UTC-substring day judging, chip edit popover seeding the UTC clock, dialog-typed times stored as a UTC clock) are all fixed. The invariant going forward: typed/displayed times are LOCAL wall-clock — `buildIso`/`toTimeSlot` and `splitOvernightEvents`' day-membership check all read/write via local `Date` getters (`getFullYear`/`getMonth`/`getDate`/`getHours`/`getMinutes`), never UTC ISO substrings. The persisted/round-tripped ISO on `CalendarEvent.start`/`end` is always a real UTC instant — only the LOCAL reading of that instant changed. Any app code that derives a calendar "day" from an ISO string must use local `Date` getters to match the library, not UTC substring slicing.
