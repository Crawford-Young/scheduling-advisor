- **`WeekCalendarView` resyncs via `resyncToken` (`@crawfordyoung/ui` ≥0.20.0) — no remounts.** It seeds internal state once and applies move/resize/delete/drag-create optimistically; bumping the `resyncToken` prop's identity forces it to re-seed from the current `events` prop IN PLACE (never remounted, so in-calendar week navigation survives). `CalendarClient` routes every path through two helpers: `refreshAndResync()` (every server-mutating success AND error path — sets `refreshQueuedRef`, runs `router.refresh()` inside a tracked `useTransition`, and a `useEffect` bumps the token once that transition settles so the re-seed reads the FRESH events prop, not stale ones) and `resyncNow()` (immediate bump, no refresh — the delete-cancel path only). `confirmedRef` discriminates delete confirm-vs-cancel so a confirmed delete's `onOpenChange(false)` does not fire a second immediate bump on top of the confirm path's bump. There is NO `key`/`resetKey` remount machinery — do not reintroduce it. **Any change whose visible effect flows through WeekCalendarView MUST state its resyncToken interaction explicitly in the task spec** — the library renders exclusively from internal `localEvents`, re-seeded ONLY on a token identity change, so "filter/modify the events prop" is invisible until a bump; regression tests for this class assert the token bump (pending-promise ordering), never the prop value, because mocked-lib unit tests render the prop directly and pass green on invisible changes (hit twice: sleepEnabled Wave 2.1, hidden-group overlay w2.6 S14 — opus impl + review both missed it). **Completed events are fully mutable** — edit, move, and resize all route through the normal `updateEvent` persist path like any other event; only the manual `locked` flag (set via the chip's lock toggle) gates move/resize, and that gate is enforced client-side by the library itself.
- **Calendar week URL sync (Wave 2.5):** `?week=YYYY-MM-DD` (validated in `calendar/page.tsx` via `resolveWeekStart`, `src/lib/calendar-week-param.ts`) seeds `defaultWeekStart`; `WeekCalendarView.onWeekChange` mirrors in-calendar navigation back into the URL via `router.replace('?week=…', {scroll:false})`, preserving all other query params (`new URLSearchParams(window.location.search)` + `params.set('week', …)`). **Known limitation (spec-accepted, do NOT "fix"):** the library week is uncontrolled/seed-only, so browser back/forward changes `?week=` but the displayed week does not follow — only a reload re-seeds from the URL. The controlled-week alternative was rejected at debate.
- **Activity model (Wave 3):** the old polymorphic `tasks` table (task/goal types, recurrence groups, tombstones) and the `check_ins` table were dropped in migration 0019 — the app now runs entirely on `activities` (templates) + `events` (independent originals). An **activity** is a template: min/max session length, a weekly session target, and a per-day `schedule` (`readonly ActivityScheduleSlot[]`, `{ day: 0-6, startMinutes, durationMin }`) in the activity's IANA `timeZone`. An **event** is a fully independent row — `activityId` is nullable (`null` = standalone); editing one event never touches another; there is no shared-field sync and no grouped writes/deletes.
  - **Generation** (`src/lib/event-generation.ts`, pure, no auth/db) is a sliding-window, TZ-aware core: on an `HORIZON_WEEKS = 8` window from now, it creates a seed for each schedule slot only when `slotStart > activity.generatedThrough`, then the caller advances `generatedThrough` to the window end. A pattern edit (`updateActivity` detecting a schedule/timeZone diff) resets `generatedThrough = now` and regenerates inline — completed/past events are never rewritten or deleted. Deleting events never resurrects them later (no tombstones — the high-water mark alone is the guard). The read-path sweep is `safeGenerateEvents()` (`src/server/actions/event-generation.ts`, zero-arg, auth-derived `userId` — never accepts a client-supplied `userId`, see the security note below).
  - **Weekly fit** (`src/lib/weekly-fit.ts`, pure) replaces streaks: `completed` events with a given `activityId`, counted in the LOCAL wall-clock week (Sunday–Saturday), divided by that activity's `weeklyTargetSessions`. Local `Date` getters only — never UTC substrings (see the local-wall-clock invariant below).
  - **Security:** the internal generation helpers (`generateEventsForActivity`, `generateEvents(userId)`) live in a PLAIN module (`src/server/generation.ts`, no `'use server'`, import-only, never client-reachable) — the `'use server'` file `src/server/actions/event-generation.ts` exports only the zero-arg, auth-gated `safeGenerateEvents()`. A `'use server'` export taking a client-supplied `userId` for a cross-user write is a Critical finding, not a valid alternate shape.
  - **Activities page** (`/activities`): one row per activity template — Title · Pattern (`formatPatternLabel(schedule, use24h)`, e.g. "Mon/Wed/Fri · 3×/wk", "No schedule" when empty) · This week (weekly-fit "2 of 3" + a `Progress` bar) · Next event (earliest future `startAt` across that activity's events) · Actions (edit via `ActivityTemplateDialog`, delete — future pending events only, past events kept). A one-off events section below the table lists standalone (`activityId IS NULL`) upcoming events with independent edit/delete/complete-toggle. `?edit=<activityId>` deep-links the edit dialog open (re-seeds from the current row on every open — close→reopen freshness).
  - **Calendar surface:** drag-create opens the library's `createActivityOptions` picker (existing activities + "No activity" + "New activity…"); picking "New activity…" opens `ActivityTemplateDialog`, then `createActivity` followed by `createEvent` for the drawn slot. `onEventEditActivity` routes to `/activities?edit=<activityId>`. All other event mutation (edit/move/resize/delete/complete/lock) routes through the independent `createEvent`/`updateEvent`/`deleteEvent` actions — never a grouped or template-wide write.
- **Chip lock (`@crawfordyoung/ui` ≥0.19.0):** `events.locked` seeds the chip's lock icon via `toLibraryEvent`; `updateEventSchema` carries an optional `locked: z.boolean().optional()`, passed through untouched by `updateEvent`. Toggle wiring is view-level — `WeekCalendarView`'s `onEventToggleLock` prop (the chip-level prop is the differently-named `onToggleLock`; do not conflate them) calls `handleToggleLock`, which reads the row's PERSISTED locked state from `events` (not the library's optimistic event) and flips it via `updateEvent({ id, locked: !currentlyLocked })` — a server-truth flip, not a library-optimistic-value flip. Two QA traps fixed: (1) the localStorage/viewport reads live in a post-mount `useEffect`, NOT the `useState` initializers — reading them during render diverges from SSR (window undefined) and triggers a hydration mismatch that silently drops the persisted position on reload; (2) pointer capture is acquired LAZILY on the first drag-threshold crossing in `handlePointerMove`, never on `pointerdown` — capturing on down retargets the synthetic click off the ChatFab button so a plain click can't open the panel. Click-vs-drag is a 5px threshold (`DRAG_THRESHOLD_PX`); `consumeDrag()` gates the click handler so a drag release never opens the panel.
- **Ephemeral quick-schedule lane:** `POST /api/chat` with `{ messages, mode: 'quick-schedule' }` (no `conversationId`) — no conversation/message rows are ever read or written; transcript capped at 6 messages by `chatRequestSchema`. Persisted requests send `{ messages, conversationId }` and always resolve to `advisor`. UI entry is `QuickScheduleInput` mounted in the app topbar (`src/app/(app)/layout.tsx`), hidden on `/chat/*`.
- **Prompt caching + weighted token deduction:** the route sends two system messages — a stable prefix flagged `providerOptions.anthropic.cacheControl: { type: 'ephemeral' }`, then the volatile context block (dates/user data) OUTSIDE the cached prefix. Keep mode `buildSystem()` output stable (no dates, no user data) or the cache silently invalidates. Deduction uses `computeWeightedTokens` (`src/lib/chat/token-weights.ts`): cache reads 0.1×, cache writes 1.25×, uncached input/output 1×. Verify caching after prompt changes via the `chat token usage` log line (`cacheReadInputTokens > 0` on a repeat turn).
- **`token-balance-changed` CustomEvent contract.** Dispatched on `window` after any token spend (chat `onFinish` callback). `TokenChipLive` in the app layout listens and refetches the balance via `getTokenBalanceAction`. Any new token-spending feature **must** dispatch `new CustomEvent('token-balance-changed')` on `window` so the topbar stays in sync.
- **Profile is identity + search only (A8, activity-model wave).** `src/server/queries/profile.ts` exports `getProfileByUsername` (identity: name/username/image/bio/createdAt) and `searchUsers`/`escapeLikePattern` (users-table search) — that is the entire surface. The `/u/[username]` page (`src/app/(app)/u/[username]/page.tsx`) renders only the identity card (`ProfileHeader`). The previous streaks/stats/activities-list/read-only-week-view sections and their backing queries (`getProfileStreaks`, `getProfileStats`, `getProfileActivities`, `getProfileWeekEvents`) and component (`profile-week-view.tsx`) were removed — they were entirely `tasks`-table-backed and had no equivalent in the new activities/events model. **Profile v2** (activities/events-backed stats + a visibility model) is a queued follow-up wave; do not reintroduce ad hoc task-shaped profile queries in the meantime. New profile surfaces still MUST add queries to `profile.ts`, never inline db reads in pages.
