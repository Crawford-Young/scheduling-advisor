- **Activity model (Wave 3) + event-series model (event-series wave):** the old polymorphic `tasks` table (task/goal types, recurrence groups, tombstones) and the `check_ins` table were dropped in migration 0019 — the app initially ran on `activities` (templates carrying their own per-day `schedule`) + `events` (independent originals). The event-series wave then extracted recurrence off the activity entirely: migration 0021 added the `event_series` table (+ `events.seriesId`, backfilling one weekly `event_series` row per activity from its old `schedule`), and migration 0022 dropped `activities.schedule`/`timeZone`/`generatedThrough`. **Today:** an **activity** (`src/db/schema.ts`) is a metadata-only template — title, min/max session length, a weekly session target, no schedule of its own. An **event series** (`eventSeries` table) holds a recurrence RULE (`freq: 'daily'|'weekly'|'monthly'|'yearly'`, plus the per-freq rule fields below), fill fields (title/description/location/color) applied at generation time only, and a `generatedThrough` high-water-mark timestamp; `activityId` is nullable (`null` = standalone series, not linked to any activity). An **event** is a fully independent row — `activityId` and `seriesId` are both nullable and independent of each other; editing one event never touches another, its series, or its activity; there is no shared-field sync and no grouped writes/deletes.
  - **Per-freq rule fields** (`src/lib/schemas/series.ts`'s `createSeriesSchema`, enforced by a `superRefine` that rejects any field belonging to another freq): `daily` takes no rule fields. `weekly` takes `weekdays` only (`readonly number[]`, non-empty, ints 0–6 **Sunday-first, matching `Date#getDay()`** — verified in `src/lib/chat/weekdays.ts`'s `WEEKDAY_ORDER` and the schema's own `MIN_WEEKDAY`/`MAX_WEEKDAY` constants). `monthly` takes EITHER `dayOfMonth` (1–31, clamped to short months at generation time) OR an nth-weekday pair (`nthOrdinal` 1–4 or `-1` for "last", plus `nthWeekday` 0–6) — never both, never neither. `yearly` takes `month` (1–12) + `dayOfMonth`, both required. All four freqs accept an optional `until` (inclusive end date) and the input-only `anchorStartAt` (stripped before insert; seeds `generatedThrough` so generation begins AT the anchor, not today — `src/server/actions/series.ts`'s `ANCHOR_GENERATED_THROUGH_OFFSET_MS`).
  - **Generation** (`src/lib/series-generation.ts`, pure, no auth/db — replaces the retired `src/lib/event-generation.ts`) is a sliding-window, TZ-aware core: on an `HORIZON_WEEKS = 8` window from now, it walks each local calendar day (in the series' `timeZone`, UTC fallback when null) and creates a seed for any day matching the rule whose local start is strictly after `generatedThrough`, within the window, at/before `until`, and not already present (`existingStartAtMs` dedupe set) — then the caller (`generateEventsForSeries`, `src/server/generation.ts`) advances `generatedThrough` to `min(window.to, until)`, even when zero seeds fire, so a repeat sweep is idempotent and a fully-elapsed series' mark still tracks forward. A rule edit (`updateSeries` detecting a diff in ANY generation-affecting field — freq, weekdays, dayOfMonth, nthOrdinal, nthWeekday, month, startMinutes, durationMin, timeZone, or until) resets `generatedThrough = now`, deletes that series' future PENDING rows (`startAt > now`, past/completed untouched), and regenerates inline; a fill-field-only edit (title/description/location/color/activityId) never touches existing rows. Deleting occurrences never resurrects them later (no tombstones — the high-water mark alone is the guard).
  - **Weekly fit** (`src/lib/weekly-fit.ts`, pure, unchanged by the series wave) replaces streaks: `completed` events with a given `activityId`, counted in the LOCAL wall-clock week (Sunday–Saturday), divided by that activity's `weeklyTargetSessions`. It is NOT series-aware — it counts by `activityId` alone, same as before A9. Local `Date` getters only — never UTC substrings (see the local-wall-clock invariant below).
  - **Security:** the internal generation helpers (`generateEventsForSeries`, `generateEvents(userId)`) live in a PLAIN module (`src/server/generation.ts`, no `'use server'`, import-only, never client-reachable) — `generateEventsForSeries` trusts a caller-supplied series row with no ownership predicate on its UPDATE, so it must never be reachable except via an already-auth-checked caller (the series CRUD actions, or the bulk sweep). The `'use server'` file `src/server/actions/event-generation.ts` exports only the zero-arg, auth-gated `safeGenerateEvents()`. A `'use server'` export taking a client-supplied `userId` (or a client-supplied series row) for a cross-user write is a Critical finding, not a valid alternate shape.
  - **Series CRUD** (`src/server/actions/series.ts`, all session-auth-gated + rate-limited): `createSeries` validates against `createSeriesSchema`, verifies a supplied `activityId` belongs to the caller (`activityBelongsToUser`), inserts, and immediately calls `generateEventsForSeries` so occurrences appear on the same request. `updateSeries` is fetch-merge-revalidate: it merges the partial input onto the CURRENT row and re-validates the WHOLE merged object against the full create schema (a partial payload can't see cross-field per-freq invariants) — when `freq` is CHANGING, any rule-mode field not supplied in the input is treated as absent (not carried over from the old freq), so a weekly→monthly edit that only sends `dayOfMonth` never leaks stale `weekdays` into the merged object. `deleteSeries` takes `mode: 'keep' | 'deleteFuture'` — `'keep'` leaves every occurrence in place (the FK's `ON DELETE SET NULL` on `events.seriesId` unlinks them); `'deleteFuture'` also removes future PENDING occurrences first. Past/completed rows are untouched either way, in both delete modes.

- **`ViewTransition` toolchain split (critical trap, wave cybond-motion-pass):** `import { ViewTransition } from 'react'` works at RUNTIME only because Next aliases `react` to its vendored canary build for app-compiled code — the installed `react` package (stable, `node_modules/react`) has no such export. tsc needs `src/types/react-canary.d.ts` (`/// <reference types="react/canary" />` — do not delete it; the app builds/runs fine without it but tsc fails). vitest resolves the REAL installed react, so any test rendering a VT-wrapped page or `loading.tsx` needs a partial mock: `vi.mock('react', async (importOriginal) => ({ ...(await importOriginal()), ViewTransition: ... }))` — see the 5 co-located `page.test.tsx` files (`calendar`, `activities`, `tokens`, `feed`, `u/[username]`) for the canonical form. Never alias `react` to the vendored canary copy in `vitest.config.ts` (react-dom internals mismatch). The general lesson: an "import X from Y works" premise about this API must be verified per CONSUMER TOOLCHAIN (bundler/runtime alias, tsc types, vitest resolution are three separate contexts), not per package.

- **Playwright-capture trap (browser QA scripts):** a screenshot taken BEFORE hydration completes can fabricate a hydration-mismatch console error — Playwright's `screenshot()` defaults `caret: 'hide'`, which injects `caret-color: transparent` into a focusable input (e.g. a text input mid-SSR) and React then reports a mismatch that does not exist in a real browser. Confirmed via perfect correlation across repeat runs (screenshot-during-load → error; no screenshots → clean on all routes) and zero `caret-color` anywhere in src or library dist. Console-cleanliness assertions must screenshot only after `networkidle`, or pass `caret: 'initial'`.
- **Settings section nav (settings-tabs-w1):** `/settings` carries a sticky three-tab strip (`src/app/(app)/settings/settings-nav.tsx`) whose `SETTINGS_SECTIONS` export is the single source of truth for the `<section id>` values the page renders — a new settings section is added THERE, not by hand-typing an id in `page.tsx`. It is a `<nav aria-label="Settings sections">` of `Button asChild` anchors, deliberately **not** Radix `Tabs`: all three sections stay in the DOM, so `role="tablist"` would misdescribe the page. Scrolling is native anchor behavior plus a reduced-motion-scoped `main { scroll-behavior: smooth }` in `globals.css` (AppShell's `<main>` is the scroll container — the document never scrolls — and it takes no className, so the rule cannot live in the component). Active state resolves observer > URL hash > first section; the hash is read via `useSyncExternalStore` because a `useState` initializer reading `window` is the repo's hydration trap and a `setState` in an effect body is a `react-hooks/set-state-in-effect` lint ERROR. **The nav MUST stay outside `StaggerReveal`** — it wraps every child in a transformed `motion.div`, which becomes the containing block and silently kills `position: sticky`; no unit test can catch that (happy-dom does no layout), so it is browser-QA-only. One CSS custom property, `--settings-nav-h`, drives the sections' `scroll-mt`; its value is verified against the rendered strip height at QA, not trusted from arithmetic (the `border-b` made it 69px, not the 68px the class list predicts). The last section carries `pb-32` for reading room, and because a spacer that small can never lift it into the spy band, the observer treats "scroll container bottomed out" as "last section is current" — guarded by `scrollHeight > clientHeight`, since an unlaid-out container reports every scroll metric as `0`.
