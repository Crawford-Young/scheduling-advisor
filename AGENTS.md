- **`WeekCalendarView` resyncs via `resyncToken` (`@crawfordyoung/ui` ≥0.20.0) — no remounts.** It seeds internal state once and applies move/resize/delete/drag-create optimistically; bumping the `resyncToken` prop's identity forces it to re-seed from the current `events` prop IN PLACE (never remounted, so in-calendar week navigation survives). `CalendarClient` routes every path through two helpers: `refreshAndResync()` (every server-mutating success AND error path — sets `refreshQueuedRef`, runs `router.refresh()` inside a tracked `useTransition`, and a `useEffect` bumps the token once that transition settles so the re-seed reads the FRESH events prop, not stale ones) and `resyncNow()` (immediate bump, no refresh — the delete-cancel path only). `confirmedRef` discriminates delete confirm-vs-cancel so a confirmed delete's `onOpenChange(false)` does not fire a second immediate bump on top of the confirm path's bump. - **Activity model (Wave 3):** the old polymorphic `tasks` table (task/goal types, recurrence groups, tombstones) and the `check_ins` table were dropped in migration 0019 — the app now runs entirely on `activities` (templates) + `events` (independent originals). An **activity** is a template: min/max session length, a weekly session target, and a per-day `schedule` (`readonly ActivityScheduleSlot[]`, `{ day: 0-6, startMinutes, durationMin }`) in the activity's IANA `timeZone`. An **event** is a fully independent row — `activityId` is nullable (`null` = standalone); editing one event never touches another; there is no shared-field sync and no grouped writes/deletes.
  - **Generation** (`src/lib/event-generation.ts`, pure, no auth/db) is a sliding-window, TZ-aware core: on an `HORIZON_WEEKS = 8` window from now, it creates a seed for each schedule slot only when `slotStart > activity.generatedThrough`, then the caller advances `generatedThrough` to the window end. A pattern edit (`updateActivity` detecting a schedule/timeZone diff) resets `generatedThrough = now` and regenerates inline — completed/past events are never rewritten or deleted. Deleting events never resurrects them later (no tombstones — the high-water mark alone is the guard). The read-path sweep is `safeGenerateEvents()` (`src/server/actions/event-generation.ts`, zero-arg, auth-derived `userId` — never accepts a client-supplied `userId`, see the security note below).
  - **Weekly fit** (`src/lib/weekly-fit.ts`, pure) replaces streaks: `completed` events with a given `activityId`, counted in the LOCAL wall-clock week (Sunday–Saturday), divided by that activity's `weeklyTargetSessions`. Local `Date` getters only — never UTC substrings (see the local-wall-clock invariant below).
  - **Security:** the internal generation helpers (`generateEventsForActivity`, `generateEvents(userId)`) live in a PLAIN module (`src/server/generation.ts`, no `'use server'`, import-only, never client-reachable) — the `'use server'` file `src/server/actions/event-generation.ts` exports only the zero-arg, auth-gated `safeGenerateEvents()`. A `'use server'` export taking a client-supplied `userId` for a cross-user write is a Critical finding, not a valid alternate shape.
  - **Activities page** (`/activities`): one row per activity template — Title · Pattern (`formatPatternLabel(schedule, use24h)`, e.g. "Mon/Wed/Fri · 3×/wk", "No schedule" when empty) · This week (weekly-fit "2 of 3" + a `Progress` bar) · Next event (earliest future `startAt` across that activity's events) · Actions (edit via `ActivityTemplateDialog`, delete — future pending events only, past events kept). A one-off events section below the table lists ALL standalone (`activityId IS NULL`) events — past included, ascending by `startAt` (`getStandaloneEvents`; the old upcoming-only filter was removed at W2 QA-R2 because past one-offs became uneditable once off the list) — with independent edit/delete/complete-toggle. `?edit=<activityId>` deep-links the edit dialog open (re-seeds from the current row on every open — close→reopen freshness).
  - **Calendar surface:** drag-create opens the library's `createActivityOptions` picker (existing activities + "No activity" only — the "New activity…" picker entry was REMOVED by a QA Round 3 amendment; explicit header buttons replaced it: "New activity" opens an empty `ActivityTemplateDialog` with no follow-up event popover, "New event" opens `EventFormDialog` `mode="create"` seeded with `nextFullHourRange()`). `onEventEditActivity` routes to `/activities?edit=<activityId>`.
