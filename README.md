# Cybond

Scheduling app built around activities, events, and event series. An **activity** is a metadata-only template (title, min/max session length, a weekly session target) — it carries no schedule of its own. An **event series** holds a recurrence rule (daily, weekly, monthly, or yearly) plus fill fields (title/description/location/color) and a `generatedThrough` high-water mark; a rolling 8-week sliding-window sweep materializes independent **events** from it — ordinary, fully editable calendar rows with no shared-field sync back to the rule. A **weekly fit** score (completed sessions ÷ weekly target, derived on read) replaces streaks. Cybond's AI assistant helps you find time and reschedule around your real calendar.

## Features

- **Week calendar (home)** — full CRUD on calendar events:
  - Drag-create: drag an empty slot to open the library's picker — pick an existing activity or "No activity" (standalone event). Header buttons cover the rest: "New activity" opens an empty activity template dialog (metadata only — no schedule to fill in), "New event" opens the event dialog seeded with the next full hour; turning on Repeat there creates an event series instead of a single event
  - Edit: the app's `EventFormDialog` for any event; editing one occurrence never touches another or the series that generated it (events are independent originals — no shared-field sync, no grouped writes). A series' own recurrence rule (frequency, days/date, end date) is edited from the Activities page, not the calendar
  - Reschedule: drag or resize events; completed events are locked and snap back
  - Lock: click the padlock icon on a chip to pin it in place — locked events can't be dragged or resized (resize handles disappear), but stay fully editable otherwise (complete, delete, edit all still work)
  - Delete: confirm dialog, optimistic UI with automatic restore on error or cancel. Deleting a generated event never resurrects it later — the generator only ever creates events after its series' high-water mark (`generatedThrough`), so there are no tombstones to maintain. Deleting a whole series (from the Activities page) offers "Keep events" (unlink, keep every occurrence) or "Delete future events too" (removes future pending occurrences; past and completed ones are always kept)
  - Wake→sleep window by default (hours from Settings, default 9–17); the Sleep mode toggle switches to a full 24h grid with shaded sleep zones where drag-create is blocked
- **Activities** — `/activities` lists your activity templates: title, a Pattern column listing every recurring series linked to that activity (e.g. "Mon/Wed/Fri · 9:00 AM · 30m", one line per series with its own inline edit/delete — "No series" when none are linked), this week's fit ("2 of 3" + a progress bar), and the next upcoming event across all its series. Edit opens the template dialog — metadata only now (title/color/description/location/duration bounds/weekly target), there's no schedule to edit here; delete removes future pending events for that activity but keeps past ones, and unlinks (never deletes) any series still generating for it. A **Repeating events** section lists series that aren't linked to any activity, with the same pattern label, next-occurrence, and inline edit/delete. Editing a series' recurrence rule regenerates its future pending occurrences — past and completed ones are always kept; deleting a series offers "Keep events" or "Delete future events too" (see above). A **One-off events** section below lists standalone events with no activity or series link — past ones included, so they stay editable — with the same edit/delete/complete affordances. Search (`?q=`) and a `+ New` button that opens the template dialog.
- **Cy chat popup** — a chat bubble on every app page opens an in-place popup that resumes your latest conversation; the assistant can read your activities, their linked series, and this week's schedule, create activities (metadata-only templates — pair them with an event or a repeated proposal to actually put time on the calendar) and events (including a bulk "create N events" tool for one-off batches), and propose actions you confirm or deny. New chat starts fresh (no conversation is saved until you send), and Expand hands the same conversation off to the full `/chat` page. Drag the bubble anywhere — it glides to the nearest screen corner, the popup opens beside it, and the spot is remembered
- **Event approval cards** — when Cy proposes a calendar event, an approval card shows it dashed on that day's schedule preview; ✓ creates it instantly (and it appears on the `/chat` page's live week calendar), ✗ sends your reason back so Cy revises. Ask for a repeated event ("work every weekday 9–5", "gym daily for a month") and Cy proposes ONE recurring series (daily, weekly, or monthly) — the card summarizes the cadence ("Repeats weekly · Mon–Fri · 8 weeks") and the anchor-day preview carries a "repeats" badge; ✓ creates a real event series, the same kind you'd get from the Activities page — its occurrences generate server-side on the usual rolling 8-week window, not as a batch of independent one-off events. The series then shows up under Activities → Repeating events for future edits or deletion. Expanding the popup while a proposal is still pending carries the card to `/chat`, where it re-renders fully actionable (still ✓/✗)
- **Model picker per conversation** — choose Sonnet (×1) or Opus (×2) from the chat header; the choice is saved on the conversation and priced into every reply
- **Tokens** — the app is free to use; tokens purchase AI assistance (Cy chat). Buy a monthly subscription (Starter/Growth/Pro) or one-off token packs at `/tokens`; cached prompt input is billed at a discount
- **Auto-delete (TTL)** — pending, standalone (non-activity) events older than `calendarPrefs.ttlDays` days past their end are hard-deleted on read; events generated from an activity are never auto-deleted. This includes occurrences from a standalone series (no linked activity) — TTL keys on "no activity" only, so a standalone series' generated occurrences are eligible for cleanup like any other standalone event
- **Friends** — send a friend request from anyone's profile (Add friend → Requested, click to cancel); the other person sees Accept/Decline on theirs. `/friends` lists your Incoming requests, Sent requests, and Friends in one place, and an accepted friend gets a Remove friend option from their profile. Pending requests don't count as friends yet — see the Visibility setting below
- **Public profiles** — every user gets an identity card at `/u/[username]` (name, avatar, bio, member-since) plus a read-only week calendar of that person's schedule, and can be found via search on `/feed`; edit your own name, bio, and username from Settings. Usernames are 3–20 lowercase letters, numbers, and underscores, unique across the app, and a short list of role and brand names is reserved; a name that is taken or reserved is refused with the same "not available" message. The first name you pick can be corrected once, right away — after that correction you can change it once every 14 days. Having no username at all stays valid forever — the profile page and search simply skip you until you pick one. Every event and series has a Visibility setting — Public (full details to anyone), Friends (full details to accepted friends only; everyone else sees a time-span-only "Busy" block), Busy (time span only, shown as an unlabeled "Busy" block, to anyone), or Private (excluded entirely) — that controls what a viewer other than the owner sees on this week view; new events default to your Settings → Calendar "Default visibility" choice. The profile's own week view is browse-only (no create/edit/delete/complete) — it's meant for checking someone's availability, not managing their calendar. A richer profile (stats) is a planned follow-up wave
- **Global search (Ctrl/⌘+K)** — a centered search field in the top bar opens a results dropdown on focus (Ctrl/⌘+K focuses it from anywhere, or closes it if already open) and searches your events (upcoming first), your activities, your reflections (Cy conversations, by title), other users, and app pages from one input; results arrive per group as each lookup finishes, and picking an event lands on its calendar week
- **Google Calendar connect (opt-in)** — signing in asks for identity only (no calendar permissions). Connecting your Google Calendar is a separate, optional step from Settings → Integrations (or an inline prompt when accepting a schedule suggestion needs it): a second consent asks for just two granular scopes (edit events, read free/busy). Disconnect any time — it revokes the grant at Google and deletes the stored tokens. OAuth tokens are encrypted at rest (AES-256-GCM) with an app-held key
- **Motion & arrival** — a cinematic splash (brand wordmark + rotating quote) plays once per browser session on any cold load, then morphs into the sidebar brand mark. App pages crossfade via native View Transitions with staggered section reveals and matching skeleton loading states, and a topbar progress line surfaces on any navigation that takes over 150ms. Sidebar navigation is client-side (no full page reloads)

## Stack

## Development

```bash
pnpm install
just dev          # dev server at :3000
just test         # vitest with coverage (100% statements/functions/lines enforced)
just e2e          # playwright
just lint         # eslint + prettier
just typecheck    # tsc --noEmit
just check        # full CI suite: lint, typecheck, test, e2e
```

Copy `.env.example` to `.env.local` and fill in all values — `t3-env` validates at startup. `TOKEN_ENC_KEY` is the OAuth-token encryption key: 32 random bytes, base64-encoded (`node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`). Rotating it invalidates every stored calendar connection (users just re-connect).

## Architecture notes

- Mutations are Server Actions with Zod validation at every boundary; API routes exist only for externally-consumed endpoints (chat, webhooks, health).
- `WeekCalendarView` (library, `@crawfordyoung/ui` ≥0.23.0) applies moves/resizes/deletes optimistically and re-seeds from the `events` prop in place when its `resyncToken` prop changes — no remounts. `CalendarClient` bumps the token after `router.refresh()` settles (`refreshAndResync()`, all server-mutating paths) and immediately via `resyncNow()` on the no-server delete-cancel path.
- `ActivityTemplateDialog` (create/edit a metadata-only activity template) and `EventFormDialog` (create/edit a single event, with an optional Repeat section that submits an event series instead) are app-owned (`src/components/forms/`), built on the library's `FormDialog` shell (`@crawfordyoung/ui` ≥0.28.1). All-day events persist real 00:00–23:59 instants plus an `allDay` flag — never a null start.
- Generation is a pure, TZ-aware, sliding-window core (`src/lib/series-generation.ts`): on a rolling 8-week horizon, an `event_series` row's sweep walks each local calendar day in the series' IANA time zone, creates a seed for any day matching its recurrence rule (daily; weekly on selected weekdays; monthly by day-of-month or nth-weekday; yearly by month+day) whose local start is strictly after the series' `generatedThrough` high-water mark and at/before an optional `until` bound, then advances `generatedThrough` to the window end (or `until`, whichever is sooner) — even when nothing generates, so a repeat sweep is idempotent. A rule edit (any field that changes what/when it generates) resets `generatedThrough = now` and deletes+regenerates that series' future PENDING occurrences inline; past and completed rows are never rewritten, and deleted occurrences never resurrect — the high-water mark alone is the guard, there are no tombstones. An activity template carries no schedule of its own anymore; it's linked to zero or more series instead.
- Weekly fit (`src/lib/weekly-fit.ts`) is derived on read: completed events with a given `activityId`, in the local wall-clock week, divided by that activity's `weeklyTargetSessions` — unaffected by series linkage. Local `Date` getters only — never UTC substrings.
- `TaskTimeFields`, `buildIso`, and `toTimeSlot` are bundled in `@crawfordyoung/ui` and consumed by the app's dialogs; the app does not duplicate them. Typed/displayed times are LOCAL wall-clock throughout the calendar and dialogs — the persisted ISO on an event's start/end is always a real UTC instant, only the local reading of that instant changed.
- Calendar chip locking (`@crawfordyoung/ui` ≥0.19.0): the `locked` boolean on `events` seeds the chip's lock icon; toggling it flips the persisted flag via `updateEvent({ id, locked })`. Lock scope is move/resize only — complete-toggle, edit, and delete all stay available on a locked event, and there is no server-side time-guard (client-side gating only, by design).
- Google OAuth is split into two flows: base sign-in requests identity scopes only (`openid email profile`), while the calendar connect flow (Settings → Integrations, or the suggestion card's inline prompt) adds exactly `calendar.events` + `calendar.freebusy` via incremental auth (`include_granted_scopes`), with offline access and forced consent so a refresh token is always issued. Account sync merges on re-login — scopes union, and a tokenless base sign-in never clobbers the stored refresh token. Tokens are encrypted at rest with AES-256-GCM (`TOKEN_ENC_KEY`, `v1:` format); disconnect revokes at Google (token in the POST body — never a URL) and nulls the stored tokens. `/api/calendar/events` answers `403 {"error":"calendar_not_connected"}` when the caller has no calendar grant, which the suggestion card turns into a connect prompt.
- The chat popup (`ChatPopup`, mounted app-wide) listens for an `open-chat` CustomEvent; dispatchers may pass `detail.prefill` to seed the input. All chat surfaces compose the single `ChatSurface` wiring.
- Error boundaries (`@crawfordyoung/ui` ≥0.22.0): every route segment ships an `error.tsx` rendering `RouteErrorFallback` with Sentry capture — root `error.tsx`, `global-error.tsx` (own html/body, imports globals.css), `(app)/error.tsx`, and all 9 segments with per-segment titles ("Failed to load calendar" etc.). Each boundary has a co-located test.
- View Transitions (Next `experimental.viewTransition`, React's native `<ViewTransition>`): every `(app)` page wraps its container in a `reveal-enter` transition — route crossfades plus a staggered `StaggerReveal` arrival, except the calendar, which stays a plain div so `WeekCalendarView` is never staggered. Every `loading.tsx` wraps its skeleton in a `reveal-exit` transition for a crossfaded skeleton→content handoff. The splash (`SplashProvider`/`SplashAnimationClient`, mounted in the root layout) hands off to the sidebar `BrandMark` via a view-transition morph (`startBrandHandoff`). Client-side sidebar navigation (`SidebarItem asChild`) reports pending navigations into `NavProgressProvider`, which surfaces a topbar `ProgressLine` after a 150ms delay.
- Friendship state lives in one `friendships` table (one row per pair, doubling as request queue and friend edge); the query that reads another user's week of events (`getProfileWeekEvents`) is the only cross-user event query in the app, and it's the sole place that resolves a viewer's friendship status against what they're allowed to see.

## Testing

- Vitest unit/integration suite lives in TWO trees, both picked up (vitest has no `include` glob): co-located `src/**/*.test.tsx` and `tests/unit/**`. Deleting or renaming a component must clean both. Coverage gates: 100% statements, functions, lines; ≥97% branches.
- Playwright e2e under `tests/e2e/` — currently unauthenticated flows only (login, redirects); authenticated e2e (seeded DB + session cookie) is planned as its own wave.
